La idea en una frase

El modelo solo sabe escribir texto. Tu aplicación es la que actúa, y trabaja sobre una copia desechable del proyecto: el contenedor.

Piensa en un experto que te ayuda por teléfono:

El experto

Qwen está en los servidores de Groq, en internet. Solo puede hablar, es decir, escribir texto. No ve tu ordenador ni toca nada.

El ayudante

Tu aplicación sostiene el teléfono. Escucha lo que pide el experto, lo hace y le cuenta qué ha pasado.

El taller

El contenedor es un taller cerrado con el proyecto roto dentro. Se puede trastear sin miedo y al acabar se tira.

Por qué hace falta un contenedor

Una tarea SWE-bench es un fallo real de un proyecto real. En el ejemplo, Django guarda un objeto en la base de datos equivocada. Para arreglarlo y comprobarlo necesitas:

  • el código de Django exactamente en la versión que tiene el fallo;
  • la versión de Python correcta, con sus librerías instaladas;
  • los tests del proyecto, listos para ejecutarse.

Prepararlo a mano es difícil, así que SWE-bench lo entrega hecho como una imagen Docker. En el ejemplo es swebench/sweb.eval.x86_64.django_1776_django-11066:latest.

  • Imagen: una foto congelada de un ordenador con todo preparado. El proyecto está en /testbed.
  • Contenedor: esa foto puesta en marcha. Lo que cambies dentro desaparece cuando se borra. Tu ordenador no se toca, y además arranca sin red (--network none).

Las piezas

Una tarea pone en marcha tres procesos de Python en tu ordenador y un contenedor. Cada proceso tiene su número (pid), que aparece en cada línea del log. Los pid cambian en cada ejecución; estos son los del ejemplo.

Lo que ve el contenedor

El contenedor solo participa en los pasos 7 y 8. No sabe que hay un modelo, ni MCP, ni un trabajador. Para él, alguien de fuera le dice «ejecuta este programa», y él lo ejecuta y devuelve lo que se imprime.

Qué hace run_tests dentro del contenedor

Es la herramienta que más trabajo hace dentro. Ejecuta el eval_script que trae la tarea con /bin/bash:

  1. Activa el entorno conda llamado testbed y configura el idioma.
  2. Ejecuta git status, git show y git diff, solo para informar.
  3. Ejecuta pip install -e . para instalar el Django de /testbed.
  4. Con git checkout y git apply añade el test nuevo de la tarea, test_existing_content_type_rename_other_database. Es el que comprueba el fallo.
  5. Ejecuta ./tests/runtests.py … contenttypes_tests.test_operations, entre los marcadores >>>>> Start Test Output y End Test Output.
  6. Con git checkout deja el fichero de tests como estaba.

Al modelo solo le llega lo que hay entre los dos marcadores. Por el paso 6, el git diff final contiene un solo fichero: el arreglo.

Código run_tests swebench_tools.py:313 recorte entre marcadores swebench_tools.py:341 get_patch swebench_tools.py:348

Cómo nace y cómo muere el contenedor

Piensa en una llamada telefónica abierta. El contenedor vive mientras el agente mantenga la línea.

  1. Nace

    El único programa del contenedor es cat. Se queda escuchando su entrada, que es una tubería que sostiene el agente.

    docker run -i --rm --name agent-smith-… \
    --network none <imagen> cat
    swebench_agent.py:89

  2. Se comprueba

    El agente espera a que Docker diga que está en marcha y mira que existe /testbed con un ls.

    _wait_until_running swebench_agent.py:102 swebench_agent.py:97

  3. Trabaja

    Cada herramienta entra con docker exec, hace su trabajo y sale. Mientras tanto, cat sigue escuchando.

    _run swebench_tools.py:195

  4. Muere

    El agente cierra la tubería: «cuelga». cat lo nota y termina, el contenedor se para y --rm lo borra. Por seguridad, después se lanza docker rm -f.

    SWEEnvironment.close swebench_agent.py:142 swebench_agent.py:152

¿Y si el agente muere de golpe con kill -9?

Un kill -9 no deja ejecutar ningún finally. Pero el sistema operativo cierra todas las tuberías del proceso muerto, así que cuelga la línea por él y el contenedor desaparece igual. La hoja de evaluación comprueba exactamente esto.

Orden de cierre al terminar la tarea

En el finally se cierra primero el Trabajador, después el Servidor MCP y por último el Contenedor. Pasa aunque la tarea haya fallado.

Código swebench_agent.py:310 SandboxSession.close sandbox_session.py:180 MCPClient.close mcp_client.py:308 SWEEnvironment.close swebench_agent.py:131

¿Por qué tantas piezas?

Cada una existe porque sin ella algo saldría mal:

Si quitáramos…pasaría que…
AgenteNadie convertiría el texto del modelo en acciones.
TrabajadorEl código del modelo se ejecutaría en el mismo proceso que tus claves de API.
Servidor MCPEl código del modelo tendría que manejar Docker él mismo. Además, la asignatura exige herramientas MCP descubiertas, no escritas a mano en el código.
ContenedorEl modelo editaría y ejecutaría un proyecto en tu propio ordenador, sin el entorno correcto y con red.
